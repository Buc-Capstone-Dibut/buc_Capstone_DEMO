## 1. 개요

이 보고서는 Dibut 플랫폼의 프론트엔드, BFF, AI 백엔드 전 계층에 걸쳐 진행한 성능 최적화 작업과, 그 작업이 기존 기능을 손상시키지 않았음을 확인한 QA·성능 검증의 결과를 정리한 것이다.

작업의 출발점은 사전에 수행한 성능·캐싱·포워딩 전수조사다. 조사 결과 48개의 개선 지점이 나왔고, 이들은 크게 네 갈래의 문제로 묶였다. 첫째, FastAPI의 비동기 핸들러가 LLM 호출이나 DB 조회 같은 동기 작업을 이벤트 루프 위에서 직접 실행해 동시 처리가 막히는 문제. 둘째, 통화·차트·캘린더처럼 일부 화면에서만 쓰는 무거운 라이브러리가 모든 페이지의 초기 번들에 실려 나가는 문제. 셋째, 서버 캐싱이 사실상 없고 공개 페이지마저 매 요청을 새로 렌더링하던 문제. 넷째, 거대한 클라이언트 컴포넌트가 무관한 상태 변경에도 통째로 다시 그려지는 문제다.

작업 내내 지킨 원칙은 무회귀(無回歸)다. 모든 변경은 동작을 바꾸지 않는 범위에서만 이루어졌고, 한 커밋에 하나의 개선만 담아 문제가 생기면 정확히 어느 변경이 원인인지 즉시 가려낼 수 있게 했다. 그 결과 23개의 작은 커밋이 `develop` 브랜치에 쌓였으며, 작업 기간 중 다른 팀원이 올린 11개 커밋과 병합되는 동안에도 회귀는 한 건도 발생하지 않았다.

## 2. 검증 방법

성능 보고서가 흔히 빠지는 함정은 "체감상 빨라졌다"는 식의 추정이다. 이를 피하기 위해 본 작업은 모든 변경을 자동·런타임 검증으로 뒷받침했고, 수치는 실제 빌드·서버·측정에서 나온 값만 사용했다.

검증은 다섯 겹으로 두었다. 우선 각 커밋마다 타입 검사(`tsc --noEmit`)와 프로덕션 빌드(`next build`)를 통과시켜 컴파일·번들 단계에서 깨지는 곳이 없도록 했다. 기존에 누적되어 있던 타입 오류 23개는 이번 작업 범위 밖이므로 손대지 않았으되, 그 수가 23개로 끝까지 유지되어 새 오류를 단 한 개도 들이지 않았음을 객관 지표로 삼았다. 다음으로 프로젝트에 이미 존재하던 자동 단위 테스트 47개를 실행했고, 백엔드는 실제 서버(uvicorn)를 띄워 엔드포인트를 호출하는 라이브 스모크로, 프론트엔드는 프로덕션 서버(`next start`)를 띄워 페이지 응답과 캐시 헤더를 직접 확인하는 방식으로 검증했다.

| 검증 수단 | 무엇을 보는가 | 결과 |
|---|---|---|
| 자동 단위 테스트 47건 | 기능 회귀 탐지 | 47건 전부 통과 |
| 타입 검사(`tsc --noEmit`) | 새 타입 오류 유입 차단 | 23건으로 불변(신규 0) |
| 프로덕션 빌드(`next build`) | 컴파일·번들 분할 | 전 구간 정상 컴파일 |
| FastAPI 라이브 스모크 | 이벤트 루프 차단 여부 실증 | 후술(3.4) |
| 프론트 런타임(`next start`) | 페이지 응답·캐시 헤더·ISR | 후술(3.3·6장) |
| `.next` 청크 측정 | 번들 분할 실측 | 후술(3.1) |

자동 단위 테스트는 면접 리포트(16건), 면접 진행 흐름(9건), 코딩 트레이닝 스펙(3건)·런너(5건)·문제은행(14건)으로 구성되며 전부 통과했다. 다만 워크스페이스처럼 자동 테스트가 없는 영역은 빌드·타입 게이트와 수동 브라우저 확인에 의존하므로, 6장과 별도 QA 계획서에 어디까지 자동으로 확인됐고 무엇이 사람 손을 거쳐야 하는지를 정직하게 구분해 두었다.

## 3. 진단과 개선

### 3.1 무거운 라이브러리의 초기 로딩

가장 먼저 손댄 곳은 라이브러리 적재 방식이다. 화상통화(LiveKit), 차트(Recharts), 캘린더(FullCalendar)처럼 특정 화면에서만 필요한 라이브러리가 정적 import로 묶여, 그것을 전혀 쓰지 않는 경로의 초기 번들까지 무겁게 만들고 있었다. 증상이 가장 심했던 것은 LiveKit이다. 통화 기능을 감싸는 `VoiceManager`가 루트 레이아웃에 상주하다 보니, 통화를 시작할 일이 없는 랜딩·로그인 페이지조차 WebRTC SDK를 내려받고 있었다. 비압축 기준 약 492KB짜리 코드가 첫 화면과 무관하게 모든 방문자에게 따라붙은 셈이다. 같은 패턴으로 마크다운 렌더러(react-markdown)는 사이트 도우미를 통해 전 경로에 실렸고, FullCalendar는 워크스페이스 대시보드의 지연 로딩 구조를 무력화하고 있었으며, Recharts는 차트가 하나도 없는 포트폴리오에서도 항상 함께 내려왔다.

조치는 네 라이브러리를 모두 `next/dynamic`으로 분리해, 실제로 그 기능이 필요해지는 순간에만 별도 청크로 받아오게 한 것이다. 통화 표면은 `active-call-overlay`라는 별도 컴포넌트로 떼어 토큰이 발급되어 통화가 활성화될 때만 마운트되도록 했고, 캘린더·아바타·마크다운은 각각 스켈레톤과 함께 지연 로드되며, Recharts는 차트 블록을 별도 파일로 추출해 차트가 실제로 그려질 때만 로드된다. 로직은 한 줄도 바꾸지 않고 import 경계만 옮긴, 회귀 위험이 가장 낮은 방식을 택했다. 비유하자면, 평소에도 텐트와 스키 장비까지 캐리어에 넣고 다니던 것을, 실제로 캠핑이나 스키를 가는 날에만 그 짐을 챙기도록 바꾼 것이다. 코드를 줄이지 않고도 "안 쓰는 페이지는 안 받는다"는 원칙 하나로 첫 로딩을 가볍게 만든 것이 핵심이다.

| 라이브러리 | 비압축 크기 | 변경 전 적재 경로 | 변경 후 로드 시점 |
|---|---|---|---|
| LiveKit SDK | 약 492KB | 모든 라우트(루트 레이아웃) | 통화 활성 시 |
| Recharts | 약 404KB | 모든 공개 포트폴리오 | 차트 렌더 시 |
| FullCalendar | 약 232KB | 워크스페이스 대시보드 | 대시보드 탭 진입 시 |
| react-markdown 외 | gzip 약 50KB | 모든 라우트(사이트 도우미) | 마크다운 표시 시 |

빌드 후 `.next` 청크를 직접 측정해 세 라이브러리가 각각 별도 비동기 청크로 분리됐음을 확인했고, `voice-manager`에 LiveKit import가 0건으로 남았음을 검사했다. 통화를 시작하지 않는 일반 페이지 기준으로 합산 약 350KB(gzip)가 초기 경로에서 빠졌다. 관련 커밋은 `3c186bd`(LiveKit), `5e87ade`(FullCalendar·아바타·마크다운), `860043a`(Recharts)다.

### 3.2 정적 자산 비대화

두 번째는 배포 용량 그 자체다. `public` 디렉터리에는 최적화되지 않은 이미지가 41.6MB 쌓여 있었고, 어디서도 import되지 않는 의존성과 과거 작업물이 함께 남아 저장소와 설치 비용을 키우고 있었다.

이미지 문제의 본질은 표시 크기와 실제 파일 크기의 불일치였다. 면접 결과를 16개 유형 카드로 보여 주는 분석 허브는 카드 썸네일을 64~176픽셀로 그리는데, 정작 원본 파일은 유형당 1MB 안팎의 PNG였다. 화면에서는 엄지손톱만 한 그림이지만 뒤에서는 한 페이지에 13MB가 내려가고 있었던 것이다. 이를 해결하려고 `sharp` 기반 사전 압축 스크립트를 만들어, 65개 이미지를 표시 용도에 맞는 너비로 줄인 뒤 무손실로 다시 인코딩했다. 여기서 의도적으로 지킨 제약이 있다. 파일명과 포맷을 그대로 두고 픽셀만 줄인 것이다. 경로를 바꾸거나 WebP로 갈아끼우면 그 이미지를 참조하는 모든 컴포넌트를 손봐야 하고 회귀 위험이 커지지만, 같은 파일명을 유지하면 코드 입장에서는 "같은 그림"이라 변경 사항이 이미지 바이너리에만 국한된다. 그 결과 압축 대상 65개가 34.3MB에서 8.2MB로, 무손실이라 화질 손상 없이 76% 줄었다.

함께 미사용 의존성 12종(puppeteer·firebase-admin·tldraw·pixi 등)을 제거해 `node_modules` 패키지 수를 약 1,125개에서 713개로 줄였다. 특히 puppeteer는 설치 때마다 Chromium 약 170MB를 자동으로 내려받는데, 코드 어디서도 쓰지 않으면서 신규 개발자의 설치 시간과 CI 빌드 시간을 갉아먹고 있었다. 여기에 참조되지 않는 미사용 아바타 GLB 3종과 작업 원본 이미지 등 약 40MB의 고아 자산을 정리했다.

| 항목 | 변경 전 | 변경 후 | 개선 |
|---|---|---|---|
| public 이미지(PNG/JPG) 총량 | 41.6MB | 8.5MB | -80% |
| 압축 대상 65개 이미지 | 34.3MB | 8.2MB | -76%(무손실) |
| 분석 허브 1페이지 이미지 전송 | 약 13MB | 약 2MB | -85% |
| node_modules 패키지 수 | 약 1,125 | 713 | -412 |
| puppeteer 설치 시 Chromium | 약 170MB | 0 | 제거 |
| 고아 자산 | 약 40MB | 0 | 삭제 |

쉽게 말하면, 명함 크기로 보여 줄 사진을 원본 고화질 그대로 보내던 것을 화면에 보이는 크기에 맞춰 줄여 보낸 것이고, 쓰지도 않으면서 짐칸만 차지하던 장비들을 내린 것이다. 무손실 재압축이라 보이는 화면은 그대로이고, 줄어든 것은 전송량뿐이다. 관련 커밋은 `d105c47`(이미지), `b2d39af`(의존성), `477cfad`·`702704a`(고아 자산)다.

### 3.3 캐싱 부재와 동적 렌더링 남용

세 번째 문제는 캐싱 전략이었다. 익명 사용자에게 공유되는 포트폴리오 페이지가 매 요청을 새로 렌더링하도록 설정(`force-dynamic`)되어 있어, 한 링크를 여러 명이 열어도 매번 데이터베이스를 조회하고 페이지를 처음부터 그렸다. 공유 링크의 속성상 같은 콘텐츠를 익명 다수가 반복해서 보는 전형적인 캐싱 적격 상황인데도, 그 이점을 전혀 살리지 못하고 있었다.

이를 두 공개 포트폴리오 페이지에 대해 ISR(주문형 증분 정적 생성, 60초 주기)로 바꿨다. 첫 요청만 실제로 렌더링하고 이후 60초 동안은 캐시에서 응답하므로, 두 번째 방문자부터는 데이터베이스 부하 없이 즉시 페이지를 받는다. 빌드 출력에서 해당 페이지가 동적(ƒ)에서 정적/ISR(●)로 옮겨졌고, 프로덕션 서버에서 실제 응답 헤더가 `s-maxage=60`으로 나오는 것까지 확인했다. 편집 후 최대 60초의 반영 지연이 생기지만, 포트폴리오라는 콘텐츠 특성상 사용자가 체감하기 어려운 수준으로 판단해 받아들였다. 함께 커뮤니티 사이드바 쿼리(최대 300행 스캔)를 5분 캐시로 묶고, 거의 바뀌지 않는 공개 바이너리(13MB 아바타 모델, 배경 이미지)에는 1년짜리 불변 캐시 헤더를 붙여 재방문 시 재다운로드 자체가 일어나지 않게 했다.

| 자산/경로 | 실측 Cache-Control 헤더 |
|---|---|
| 아바타 GLB · 포트폴리오 배경 | `public, max-age=31536000, immutable` |
| `/images` 일반 이미지 | `public, max-age=3600, stale-while-revalidate=86400` |
| 공개 포트폴리오 `/p/[handle]/[slug]` | `s-maxage=60, stale-while-revalidate` (+ `x-nextjs-cache`) |

이 절의 모든 효과는 추정이 아니라 `next start`로 띄운 실제 서버의 응답 헤더로 검증했다. 비유하면, 손님이 올 때마다 같은 메뉴를 재료부터 다시 조리하던 식당이, 한 번 만든 요리를 일정 시간 보관해 두고 같은 주문에는 그대로 내주도록 바꾼 것이다. 관련 커밋은 `73e5522`(ISR), `6ec3e37`(사이드바), `a0b0124`(불변 헤더), `ede7c28`(이벤트 맵 중복 제거), `317e550`(폰트 preconnect)다.

### 3.4 백엔드 이벤트 루프 블로킹

네 번째이자 동시성 측면에서 가장 중요한 문제는 FastAPI 백엔드에 있었다. 비동기(`async`) 핸들러 안에서 Gemini LLM 호출, PDF 파싱, 데이터베이스 쿼리 같은 동기 블로킹 작업을 이벤트 루프 위에서 직접 실행하고 있었다. asyncio는 단일 이벤트 루프 모델이라, 한 요청이 수 초짜리 LLM 호출에 묶여 있으면 그동안 다른 모든 요청이, 심지어 헬스 체크조차 함께 멈춰 서게 된다. 동시 면접이라는 이 플랫폼의 실제 부하 패턴에서 치명적인 구조다.

조치는 REST·admin 핸들러의 Gemini 호출과 DB 호출을 전부 `asyncio.to_thread`로 스레드풀에 넘긴 것이다. 이렇게 하면 블로킹 작업이 이벤트 루프 밖에서 돌고, 루프는 그동안 다른 요청을 계속 받을 수 있다. 여기에 리포트 생성 워커가 큐가 비었을 때도 1초 간격으로 헛도는 폴링을 점진적으로 10초까지 늦추도록 했고(F4), 선택적으로 켤 수 있는 커넥션 풀을 기본 비활성으로 추가했으며(F3, 무회귀를 위해 플래그가 꺼져 있으면 기존 동작 그대로), GitHub README와 파일 트리를 가져오는 두 요청이 같은 커넥션을 재사용하도록 정리했다(F5).

핵심은 "더 빠르게"가 아니라 "동시성 회복"이다. 쉽게 말하면, 주문이 오래 걸리는 손님 한 명 때문에 줄 전체가 멈춰 서던 가게에서, 오래 걸리는 조리를 주방 보조에게 넘기고 카운터는 계속 다음 손님을 받도록 바꾼 것이다. 이 효과는 실제 서버를 띄워 직접 확인했다. uvicorn으로 백엔드를 부팅한 뒤 이력서 파싱 엔드포인트를 호출하자 실제 Gemini 파싱 결과가 정상적으로 돌아왔고, 무엇보다 그 LLM 호출이 진행되는 동안에도 헬스 체크가 즉시 응답했다. 블로킹 작업이 이벤트 루프 밖으로 옮겨졌음을 보여 주는 직접 증거다.

| 호출(라이브 스모크) | 결과 |
|---|---|
| `/admin/health` | 정상(`active_sessions=148`, DB 호출이 스레드풀 경유) |
| `POST /v1/interview/parse-resume` | 실제 Gemini 파싱 JSON 반환 |
| LLM 호출 진행 중 `/health` | 즉시 응답(이벤트 루프 차단 없음) |

관련 커밋은 `a02ddad`(LLM 오프로드), `e276d59`(DB 오프로드), `9bb1f6b`(폴 백오프), `e9307b7`(커넥션 풀), `601ebeb`(httpx 재사용)다.

### 3.5 프론트엔드 과도한 리렌더링

마지막은 React 렌더링이다. 워크스페이스 상태를 담는 Zustand 스토어를 셀렉터 없이 통째로 구독하는 컴포넌트들이 있어, 스토어의 어떤 값이 바뀌든 그 값과 무관한 컴포넌트까지 줄줄이 다시 그려지고 있었다. 가장 두드러진 곳이 칸반 보드다. 카드 하나를 나타내는 `TaskCard`가 스토어 전체를 구독하고 있었고 이 카드는 보드에서 최대 500개까지 그려지므로, 카드 하나를 클릭해 활성 카드를 바꾸는 단순한 동작에도 500개 카드 전체가 다시 렌더링됐다. O(1)이어야 할 상호작용이 O(N) 비용으로 번지고 있었던 것이다.

`TaskCard`를 자신이 실제로 읽는 값(태그·우선순위)만 구독하는 슬라이스 셀렉터로 바꾸고 `React.memo`로 감싸, 자기 데이터가 바뀔 때만 다시 그려지도록 했다. 같은 방식으로 스토어를 통째로 구독하던 나머지 15곳도 슬라이스 셀렉터로 전환했다. 영상 면접실에서도 비슷한 문제가 있었다. 1초마다 도는 남은 시간 타이머가 1,400줄짜리 페이지 전체와 그 안의 WebGL 아바타, 카메라 패널까지 매초 다시 그리게 만들고 있었는데, 아바타와 카메라를 `React.memo`로 감싸 시간 표시와 무관한 이 무거운 컴포넌트들이 타이머 틱마다 다시 그려지지 않게 막았다. 협업 문서 편집기(3,400줄)는 활성 문서를 2초, 문서 목록을 5초마다 폴링하며 매번 편집기 전체를 다시 그리고 있었는데, 실시간 동기화는 이미 별도 웹소켓 채널이 담당하므로 두 폴링 주기를 모두 30초 안전망으로 늦췄다.

쉽게 말하면, 책상 위 시계의 숫자 하나를 바꾸려고 방 전체를 다시 칠하던 것을 시계 부분만 다시 칠하도록 바꾼 것에 가깝다. 화면에 보이는 결과는 똑같지만, 보이지 않는 곳에서 불필요하게 반복되던 그리기 작업이 사라진다.

| 변경 지점 | 변경 전 | 변경 후 |
|---|---|---|
| TaskCard 카드 1개 클릭 시 리렌더 | 약 500개 카드 전체 | 해당 카드만 |
| 스토어 통째 구독 컴포넌트 | 16곳 | 0곳(전부 슬라이스 셀렉터) |
| 영상룸 1초 타이머 시 아바타·카메라 | 매초 리렌더 | 리렌더 스킵 |
| 문서 편집기 백그라운드 폴링 | 2초 / 5초 | 30초 / 30초 |

관련 커밋은 `8e023b1`(TaskCard), `666047f`(나머지 15곳), `ec58060`(아바타·카메라 memo), `ec385a3`(문서 폴링 완화)다.

## 4. 페이지별 영향

위의 개선들이 실제 화면에서 누구의 어떤 경험을 바꿨는지를 라우트 단위로 정리하면 다음과 같다. 근거 수치는 커밋과 검증 로그에 실재하는 값만 적었고, 측정하지 않은 항목은 수치를 만들어 내지 않고 정성적으로 남겼다.

| 페이지 | 주 사용자 | 변경 전 체감 문제 | 적용한 최적화 | 변경 후 |
|---|---|---|---|---|
| 랜딩 `/` | 첫 진입 익명 방문자 | 통화와 무관한 첫 화면이 LiveKit·캘린더·아바타·마크다운까지 끌고 들어옴 | 무거운 라이브러리 지연 로드, 폰트 preconnect | 면접용 무거운 코드를 더는 첫 화면에서 받지 않음 |
| 공개 포트폴리오 `/p/[handle]/[slug]` | 공유 링크 수신자(채용담당자·교수 등 비로그인) | 매 요청 풀 렌더, 캐시 없음, Recharts 즉시 적재 | ISR 60초 + Recharts 지연 로드 | 두 번째 방문자부터 캐시 응답, 차트는 필요 시에만 |
| 워크스페이스 보드 `/workspace/[id]` | 협업 팀원 | 카드 하나 옮길 때 보드 전체 리렌더, 문서 뷰 상시 폴링 | 슬라이스 셀렉터 + memo, 폴링 2s/5s→30s | 해당 카드만 갱신, 유휴 보드의 배경 재렌더 제거 |
| AI 영상면접 `/interview/room/video` | 면접 지원자 | 1초 타이머가 아바타·카메라까지 매초 리렌더, SDK 조기 적재 | 아바타·카메라 memo, LiveKit 지연 로드 | 초당 리렌더가 무거운 패널로 번지지 않음 |
| 면접 분석·리포트 `/interview/analysis` | 동시 면접자 | 리포트 생성(동기 LLM/PDF)이 이벤트 루프를 막아 다른 요청 대기 | 블로킹 작업 오프로드 + 폴 백오프 | 한 명의 리포트 생성이 다른 요청을 멈춰 세우지 않음 |
| 커뮤니티·사이드바 `/community/*` | 일반·협업 사용자 | 사이드바가 페이지마다 DB 조회, 정적 페이지도 동적 렌더 | 사이드바 5분 캐시, 정적 페이지 재정적화 | 사이드바 캐시 응답, 정적 페이지 정상화 |
| 이력서·공고 파싱(BFF→FastAPI) | 면접 지원자 | 큰 PDF 파싱이 루프를 점유해 다른 요청 응답 지연 | 파싱 경로 블로킹 작업 오프로드 | 무거운 파싱 중에도 타 요청이 함께 막히지 않음 |
| 정적 이미지 자산 | 익명·재방문자 | 캐시 헤더 부재로 매번 재다운로드, 원본 과대 | 불변 헤더 + 무손실 재압축(34→8MB) | 재방문 시 캐시 즉시 표시, 전송량 자체 감소 |

가장 큰 수혜를 본 화면은 셋이다. 첫째는 공개 포트폴리오다. 링크 하나에 여러 사람이 몰리는 패턴에서 ISR이 두 번째 방문자부터 캐시로 응답하니, "남이 열어보는 화면"의 첫인상이 그대로 개선된다. 둘째는 면접 분석·리포트 경로다. 동시 면접 상황에서 한 사람의 리포트 생성이 다른 지원자의 요청을 줄 세우던 동시성 병목이, 이 플랫폼의 핵심 가치인 AI 모의면접에서 정확히 풀렸다. 셋째는 워크스페이스 보드다. 여러 명이 동시에 카드를 드래그하는 협업일수록, 보드 전체 리렌더가 사라진 이득이 누적된다.

## 6. QA 테스트 결과

성능 개선이 기능을 깨뜨리지 않았는지는 별도의 회귀 테스트 계획서(`docs/qa/2026-06-03-regression-test-plan.md`, 7개 영역 95개 테스트 케이스)에 정리했고, 그중 자동·스모크·빌드·런타임으로 확인 가능한 항목은 이번에 실제로 실행했다.

자동 단위 테스트 47건은 전부 통과했다. 타입 검사는 23개 커밋 전 구간에서 기존 오류 23개를 그대로 유지해 새 오류를 들이지 않았고, 프로덕션 빌드는 매 단계 정상 컴파일됐다. 백엔드는 실제 서버를 띄워 헬스 체크, 세션 목록, 이력서 파싱을 호출해 정상 응답을 확인했으며, 앞서 적은 대로 LLM 호출 중에도 헬스 체크가 즉시 응답함을 직접 봤다. 프론트엔드는 프로덕션 서버에서 랜딩을 비롯한 다섯 개 페이지가 모두 정상(HTTP 200) 응답했고, 캐시 헤더와 ISR 동작은 실제 응답 헤더로 검증했다.

| 검증 항목 | 기준 | 결과 |
|---|---|---|
| 자동 단위 테스트 | 전 스위트 통과 | 47/47 통과 |
| 타입 검사 | 신규 오류 0 | 23→23(신규 0) |
| 프로덕션 빌드 | 매 단계 성공 | 전 구간 성공 |
| FastAPI 라이브 스모크 | 엔드포인트 정상 + 루프 무차단 | 정상, LLM 중 헬스 즉시 응답 |

정직하게, 이번 작업 환경에서 끝까지 실증하지 못한 항목을 남긴다. 브라우저나 실제 통화, 배포 환경이 있어야 확인 가능한 것들이다.

## 8. 결론

전수조사에서 나온 48개 지점을 출발점으로, 23개의 작은 커밋을 통해 프론트엔드·BFF·백엔드 전 계층에서 측정 가능한 성능 개선을 달성했다. 무거운 라이브러리(합산 gzip 약 350KB)를 첫 화면에서 걷어내고 공개 이미지를 41.6MB에서 8.5MB로 줄여 초기 로딩 비용을 구조적으로 낮췄으며, 공개 포트폴리오를 ISR로 전환하고 안정 자산에 불변 헤더를 붙여 반복 조회와 재다운로드를 캐시로 대체했다. 백엔드에서는 블로킹 작업을 스레드풀로 옮겨, LLM 호출 중에도 서버가 다른 요청을 계속 처리함을 라이브 스모크로 직접 확인했다. 프론트엔드의 과도한 리렌더링은 구독 범위를 좁혀 단순 상호작용이 화면 전체를 멈춰 세우지 않게 했다.

각 조치는 단순한 수치 개선을 넘어 "비용을 사용 시점으로 미룬다", "동시성을 회복한다", "다시 그리는 범위를 좁힌다"는 분명한 의도에 기반하며, 그 효과는 추정이 아니라 빌드·런타임·라이브 스모크 실측으로 뒷받침된다. 그리고 이 모든 변경이 자동 테스트 47건 통과, 타입 신규 오류 0, 빌드 전 구간 성공, 회귀 0건으로 기능 안정성을 훼손하지 않았음을 확인했다.
