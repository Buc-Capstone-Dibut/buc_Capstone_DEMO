한눈에 보기

이번 작업은 "AI 모의면접의 영상 녹화·분석 리포트"를 실제로 동작하는 수준까지 끌어올리고, 세 가지 면접 플로우(채용공고·직무·포트폴리오)를 시연 가능한 상태로 안정화한 것입니다. 새 기능을 늘리기보다, 이미 있는 기능이 끝까지 제대로 동작하도록 근본 원인을 찾아 고치는 데 집중했습니다.

이번에 해결한 핵심 5가지

면접이 첫 질문에서 멈추던 문제
웹소켓 연결이 특정 상황에서 거부·단절되면 "첫 질문 불러오는 중"에서 영영 멈췄습니다. 두 가지 근본 원인을 찾아 자동 복구되게 고쳤습니다.
영상이 검은 화면으로 저장되던 문제
카메라 준비 타이밍 문제로 소리만 녹음되고 화면이 검게 저장됐습니다. 스트림 도착을 기다린 뒤 녹화하도록 근본 수정했습니다.
면접관 목소리도 함께 녹음
본인 답변만이 아니라 면접관(AI) 질문 음성도 한 트랙에 섞어 녹음 — 리포트에서 질문·답변을 함께 들을 수 있습니다.
질문별 영상 하이라이트
타임라인에서 각 질문 구간만 펼쳐 보고, 그 구간의 시선·표정 요약을 함께 확인하는 UI를 새로 설계했습니다.
포트폴리오 RAG-lite
깃 레포를 분석해 DB에 저장하고, 면접 시작 시 서버가 그 분석을 다시 꺼내(retrieve) 면접관 프롬프트에 주입합니다. 프롬프트에만 의존하지 않는 구조.
저장 이중화 + 용량 절감
로컬 개발은 폴더에, 배포는 Supabase에 자동 저장. 녹화 비트레이트를 절반으로 낮춰 무료플랜 저장 여유를 2배로 확보했습니다.
결론
세 플로우 모두 시연 가능한 상태이며, 로컬·배포 양쪽에서 녹화 저장→리포트 재생까지 실측으로 확인했습니다. 남은 것은 실제 카메라로 한 번 최종 리허설하는 일입니다.

배경과 목표 — 무엇이 문제였나

"영상 저장·분석 리포트"는 기능 자체는 만들어져 있었지만, 실제로 면접을 진행해 보면 곳곳에서 조용히 실패하고 있었습니다. 사용자가 발견한 증상들을 하나씩 근본 원인까지 추적했습니다.

사용자가 겪은 증상실제 근본 원인 (추적 결과)
"첫 질문을 불러오는 중…"에서 멈춤브라우저 쿠키가 커지면(8KB 초과) 웹소켓 첫 악수(handshake)가 서버에서 400으로 거부. 또한 최초 연결이 실패하면 재시도 로직이 없어 그대로 사망.
영상이 소리만 나오고 화면이 검음카메라 준비(비동기)보다 녹화 시작이 항상 먼저 실행돼 영상 트랙 없이 오디오 전용으로 고정. 같은 이유로 시선 분석도 전 세션에서 죽어 있었음.
면접이 자연스럽게 끝나면 영상이 사라짐AI가 면접을 스스로 종료하는 경로에서 업로드·저장 절차를 건너뛰고 결과 페이지로 이동.
포트폴리오 면접이 레포 내용을 잘 못 씀레포 분석 결과가 저장은 되지만 읽는 코드가 없어, 면접관은 원본 JSON을 1,500자에서 잘라 넣는 방식으로만 사용.
공고 분석 실패가 조용히 통과실패해도 "성공"으로 응답해, 사용자는 깨진 데이터로 면접까지 진행.
작업 원칙 (Karpathy 4원칙)
① 기능을 늘리지 않는다 — 시연 범위 내 안정화에 집중. ② 근본 원인 없이는 고치지 않는다. ③ 수술적 변경 — 건드릴 곳만 최소로. ④ 검증 가능한 목표 — 고쳤다면 실측으로 증명.

기술 스택 (변경 없음)

  • 프론트엔드 · BFF — Next.js 14 (웹 화면 + API 라우트가 FastAPI로 중계)
  • AI 백엔드 — FastAPI (실시간 음성 면접·리포트 생성), Google Gemini Live
  • 데이터베이스 · 저장소 — Supabase (PostgreSQL + Storage)
  • 얼굴 분석 — MediaPipe FaceLandmarker (브라우저 내, 서버로 영상 미전송)

03

주요 작업 ① 면접 진행 안정화

면접이 시작조차 안 되던 문제를 두 겹으로 고쳤습니다. 하나는 서버 쪽 연결 거부, 하나는 클라이언트 쪽 복구 부재였습니다.

문제 A — 쿠키가 크면 웹소켓이 400으로 거부

브라우저는 로그인 쿠키를 웹소켓 연결에도 함께 보냅니다. 누적된 인증 쿠키로 헤더 한 줄이 8,192바이트를 넘으면, 웹소켓 라이브러리가 면접 서버에 닿기도 전에 400 오류로 끊었습니다.

전9KB 쿠키를 단 브라우저 → 모든 면접 연결이 400 거부 → "재연결 시도중…"만 반복
후핸드셰이크 파서의 헤더 한도를 32KB로 상향 → 2K·9K·20K·31K 쿠키 전부 정상 연결(실측)

문제 B — 최초 연결 실패 시 복구가 없음

일시적 단절이 나면 자동 재연결이 있었지만, 면접이 시작되기 전 단계에서는 재연결이 걸려 있지 않아 한 번 튕기면 그대로 멈췄습니다.

전첫 연결이 거부되면 재시도 0회 → 화면은 영원히 로딩, 오류 표시도 없음
후시작 전에도 자동 재연결(백오프) → 서버가 살아나는 순간 자동으로 면접 시작. "재연결 시도중" 안내도 정직하게 노출
검증
세 서버(웹·FastAPI·워크스페이스)를 재시작한 상태에서 프로토콜 E2E(세션 생성 → 초기화 → 첫 질문 수신)를 반복 실행해 전부 통과. FastAPI를 강제로 내렸다가 복구시켜, 화면이 자동으로 다시 연결되는 것까지 브라우저로 확인했습니다.

주요 작업 ② 영상 녹화 정상화

"소리만 저장되고 화면이 검다"는 증상의 원인은 타이밍 경쟁(race)이었습니다. 실패한 녹화 파일을 직접 부검(ffprobe)해 영상 트랙 자체가 없다는 것을 확인하고 근본 수정했습니다.

검은 화면 — 카메라보다 녹화가 먼저 시작

전카메라 준비(비동기)가 끝나기 전에 녹화가 시작 → 영상 없이 오디오 전용으로 고정. 시선 분석도 같은 이유로 전 세션 미작동
후카메라 스트림 도착을 기다렸다가 녹화 시작(실패 시 즉시 음성 전용 폴백). 산출물 확인: vp9 영상 + opus 음성, 프레임 밝기 정상(검정 아님)

면접관(AI) 음성도 함께 녹음

브라우저의 오디오 엔진에서 AI 재생 음성을 살짝 분기(tap)해, 본인 마이크와 하나의 트랙으로 믹싱했습니다. (크롬은 오디오 트랙이 여러 개면 첫 번째만 저장하므로 믹싱이 필수였습니다.)

증명 방법
440Hz 합성 마이크로 녹음한 뒤, 그 주파수를 필터로 제거해도 음성 에너지가 남아 있음을 스펙트럼으로 확인 → 면접관 음성이 실제로 섞여 있음을 정량 증명.

주요 작업 ③ 리포트 영상 분석

면접이 끝나면 리포트에서 영상을 질문 단위로 되돌아보고, 그 구간의 비언어 행동(시선·표정)을 참고할 수 있습니다. 점수를 매기지 않고 "관찰된 행동"만 담백하게 보여주는 것이 원칙입니다.

질문별 하이라이트
타임라인 아래 Q1·Q2·Q3 칩을 펼치면 그 질문 구간만 재생하는 미니 플레이어가 열리고, 구간 끝에서 자동으로 멈춥니다. 한 번에 하나만 펼쳐 영상 중복 로드를 막았습니다.
구간 시선·표정 요약
해당 구간의 정면 응시·미소 비율을 칩으로 요약. 표본이 부족하면 표시하지 않고, 점수가 아니라 참고용임을 문구로 명시합니다.
재생 영상 위 오버레이
재생 중인 얼굴 위에 시선 점·상태 점을 얹어, 어디를 보고 있었는지 직관적으로 표시. 끄고 켤 수 있습니다.
비언어 관찰 패널
정면 응시 %·미소 %·고개 움직임(낮음/보통/높음)을 요약. 감정을 단정하지 않고 관찰 가능한 행동만 기록합니다.

시간축 정밀 정렬

얼굴 분석은 인식 엔진을 불러온 뒤 시작되므로, 녹화 시작 시각과 미세하게 어긋날 수 있습니다. 이 오프셋을 보정해, 영상 위 오버레이와 구간 통계가 실제 영상 위치와 맞도록 맞췄습니다. (2차 검증에서 발견해 수정)

검증
시드(seed) 리포트에서 Q1~Q3 칩이 렌더되고, 펼치면 해당 구간(예: 0:12)으로 정확히 이동하며, 시선 오버레이 캔버스와 구간 통계 칩(이탈 20%·미소 60%)이 함께 뜨는 것을 브라우저로 확인했습니다.

주요 작업 ④ 포트폴리오 RAG-lite

"프롬프트에만 의존하지 말고, DB에서 꺼내 쓴다" — 이번 작업의 핵심 설계 포인트입니다. 거창한 벡터 검색이 아니라, 레포 분석을 DB에 저장했다가 면접 시작 시 서버가 다시 꺼내(retrieve) 면접관에게 주입하는 가벼운 방식(RAG-lite)입니다.

데이터 흐름

단계동작
① 분석공개 깃 레포 URL → GitHub API로 README·파일트리 수집 → Gemini가 요약·아키텍처·인프라 가설·감지 토픽 추출
② 저장면접 세션 생성 시 분석 스냅샷을 portfolio_sources 테이블에 저장 (기존엔 저장만 되고 아무도 안 읽던 "죽은 데이터")
③ 조회면접 시작(웹소켓) 시 서버가 세션 종류를 보고 DB에서 스냅샷을 다시 읽어 면접 상태에 병합 (retrieve)
④ 주입구조화된 텍스트(레포/README/아키텍처/가설/토픽) + 60/10/30 평가 루브릭을 면접관 시스템 프롬프트에 주입
시연 멘트 (한 줄)
"포트폴리오 면접이 시작되면 서버가 클라이언트 프롬프트가 아니라 DB에 저장된 레포 분석을 직접 조회해 면접관에게 주입하고, 설계 의도 60% · 코드 품질 10% · AI 활용 30% 루브릭에 맞춰 질문을 생성합니다."
결정적 증명

검증 방법 — 멀티에이전트 적대적 리뷰

고친 코드가 다른 걸 고장 내지 않았는지를 사람 한 명의 눈이 아니라, 여러 AI 에이전트가 서로 다른 관점으로 동시에 검사하고 서로 반박하게 하는 방식으로 검증했습니다.

검증 파이프라인

단계방식
지도 작성4~5개 에이전트가 코드베이스의 각 영역(녹화·리포트·저장·RAG·예외)을 병렬로 정독해 결합 구조를 지도화
발견 (Find)3개 관점(회귀·크로스계약·정확성)으로 결함 후보를 병렬 발굴
반박 검증 (Verify)각 발견을 다른 에이전트가 반박 시도 — 실제 코드 경로를 추적해 재현 가능한 것만 확정
수정 → 재검증확정된 결함만 수술적으로 수정하고, 기존 테스트로 회귀가 없는지 재확인
1차 리뷰 — 확정 6건
자연 종료 시 녹화 유실, 연결 끊김 중 녹화 영구 중단, 시선 시간축 어긋남 등. 전부 수정·재검증.
2차 리뷰 — 확정 3건
병렬 작업의 봉합선에서 발생한 이벤트 루프 블로킹, 실패 배너 미표시, 기계 코드 노출. 전부 수정.
왜 이렇게까지
녹화·리포트·면접 진행은 서로 얽혀 있어 "한 곳을 고치면 다른 곳이 끊기는" 구조입니다. 그래서 각 수정마다 발견 → 반박 → 재검증 사이클을 돌려, 눈으로 놓치기 쉬운 연쇄 결함까지 잡았습니다.

Next.js API

▲ HTTP · x-user-id ▼

FastAPI

저장 용량 분석 — Supabase 무료플랜

영상은 용량이 크므로, 무료플랜으로 시연이 가능한지 실제 비트레이트로 계산했습니다. 결론부터: 시연에는 충분하며, 이번에 비트레이트를 낮춰 여유를 2배로 늘렸습니다.

비트레이트 조정

전영상 1.5Mbps → 실측 ≈ 12.2 MB/분 → 7분 면접 ≈ 85MB
후영상 0.8Mbps로 하향(얼굴 분석·재생 화질엔 영향 거의 없음) → ≈ 7 MB/분 → 7분 면접 ≈ 44MB

무료플랜 한도 대비 수용량 (조정 후 기준)

무료플랜 한도1회 소요수용량판정
Storage 1 GB7분 면접 ≈ 44 MB약 22회 면접 저장시연 충분
Egress 5 GB / 월리포트 1회 시청 ≈ 44 MB약 116회 시청 / 월시연 충분
Database 500 MB세션당 시선 데이터 ≈ 25 KB수만 세션문제 없음

* 조정 전에는 Storage 기준 약 12회였습니다. 병목은 영상 저장(Storage)이며, DB·대역폭은 넉넉합니다.

운영 시 참고
여러 명이 계속 테스트하면 Storage 1GB는 실면접 20여 회에서 참니다. 장기 운영 시에는 ① 오래된 녹화 자동 정리 ② Supabase Pro($25/월, Storage 100GB) 중 하나를 고려하면 됩니다. 시연 단계에서는 현재 무료플랜으로 충분합니다.

쟁점

사용자가 "한 면접 결과"를 보려고 화면을 여러 개 오갑니다. 유지보수도 여러 곳에서 동시에 해야 합니다.

권고 — 역할 분리 + 정본화. ⑴ 세션 단위 결과는 /result를 유일한 정본으로. ⑵ /analysis는 "여러 면접을 가로지른 인사이트(성향·추세)"로 역할을 명확히 구분. ⑶ 훈련 허브·프로필의 리포트성 카드는 정본으로 링크만 걸고 중복 표시를 걷어냄. → 화면 수를 줄이는 게 아니라 "어디서 무엇을 보는지"를 한 겹으로 정리.
② 면접 플로우별로 리포트를 따로 둘 것인가
현황

채용공고·직무·포트폴리오 3개 플로우가 이미 하나의 리포트 형식으로 나옵니다(동일한 60/10/30 루브릭, 동일한 리포트 컴포넌트 재사용).

쟁점

"플로우마다 리포트를 별도로 만들어야 하나?" → 굳이 필요한가.

권고 — 통합 유지(별도 구현 불필요). 세 플로우는 데이터·라벨만 다르고 구조는 동일합니다. 별도로 나누면 3중 유지보수 부담만 커집니다. 차이는 "섹션 라벨·컨텍스트 배지"로만 표현하고, 포트폴리오처럼 특성이 있는 경우에만 블록 하나를 조건부로 추가(예: 레포 맥락)하는 방식이 가장 경제적입니다.
③ 채용공고 · 커뮤니티 등 짜잘한 UI/UX 검토
현황 · 대상 화면

채용공고 — 목록·캘린더·카드·등록 폼·면접 런치 오버레이(career/job-postings, components/features/job-postings). 커뮤니티 — 게시판·스쿼드 글쓰기(community/board/write, community/squad/write).

검토 체크리스트
  • 채용공고 — 캘린더 라벨 가독성 · 카드 정렬·빈 상태 · 등록 폼의 파싱 실패 안내(이번에 개선됨) · 첨부 미리보기 동선
  • 커뮤니티 — 글쓰기 에디터 일관성 · 목록↔작성 이동 동선 · 빈 상태 일러스트 · 작성 후 피드백
권고 — 기능 결함이 아닌 다듬기 항목이므로, 개별로 흩지 말고 "UI/UX 정리" 한 스프린트로 묶어 일괄 처리. 우선순위는 사용 빈도가 높은 채용공고 목록·캘린더 → 커뮤니티 글쓰기 순.
