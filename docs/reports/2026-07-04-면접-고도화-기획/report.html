왜 만들었나 — 기존 모의면접의 한계

Debut의 AI 모의면접은 원래 "음성으로 묻고 답하는" 형태였습니다. 대화 내용은 텍스트로 기록됐지만, 정작 면접에서 중요한 "어떻게 보였는가"는 아무것도 남지 않았습니다.

기존음성 문답 + 텍스트 리포트만. 영상 저장 없음 · 시선/표정 관찰 없음 · 되돌아볼 화면 없음
문제실제 면접은 "무엇을 말했나" 못지않게 "어떻게 보였나(시선·표정·자세)"가 평가됩니다. 그 절반이 훈련에서 통째로 빠져 있었습니다.

기획 동기

  • 실전 격차 — 사용자는 자기 답변을 다시 보고 고칠 방법이 없었습니다. 녹화가 없으니 "내가 어떻게 보였는지" 확인 불가.
  • 레퍼런스 검증 — 면접 영상을 저장하고 AI 피드백을 얹는 서비스(rehearse 등)를 분석. "녹화 + 비언어 관찰"을 더하면 훈련 가치가 크게 올라간다고 판단.
  • 차별화 — 단순 문답 챗봇이 아니라, 영상까지 되돌아보는 "고도화된 모의면접"으로 졸업작품의 완성도를 끌어올림.
기획 결론
"면접 영상을 저장하고, 비언어 행동(시선·표정·고개 움직임)을 관찰해 질문별 리포트로 돌려주는 고도화된 모의면접을 만든다." — 이 문장이 이번 개발의 출발점입니다.
지킬 원칙 (기획 단계에서 결정)
① 점수를 매기지 않는다 — 감정을 단정하지 않고 "관찰된 행동"만 참고용으로. ② 개인정보 보호 — 얼굴 영상은 서버로 보내지 않는다. ③ 시연 범위 — 새 기능을 무한히 늘리지 않고 핵심만.

무엇을 만들기로 했나 — 고도화 범위

기획 결론에 따라, 기존에 없던 기능을 아래 범위로 정의했습니다. "있으면 좋은 것"이 아니라 "고도화된 면접에 반드시 필요한 것"만 골랐습니다.

항목기존이번에 새로 만든 것
면접 영상없음카메라 녹화 + 면접관(AI) 음성까지 한 트랙에 저장
비언어 관찰없음정면 응시 · 미소 · 고개 움직임 (무점수 관찰, 감정 단정 안 함)
질문별 되돌아보기없음타임라인 + 질문별 영상 하이라이트 + 구간 시선 요약
재생 오버레이없음재생 영상 위에 시선·상태 점을 얹어 표시(끄고 켜기)
포트폴리오 면접프롬프트 의존레포 분석을 DB에서 조회해 주입하는 RAG-lite
고도화 ① 영상
면접을 통째로 녹화해 저장하고, 리포트에서 다시 재생. 로컬 개발은 폴더에, 배포는 Supabase에 자동 저장.
고도화 ② 비언어
MediaPipe로 초당 5회 시선·표정을 관찰해, "정면 응시 80%" 같은 수치와 코칭을 리포트에 제공.
고도화 ③ 리포트
질문 단위로 영상을 끊어 보고, 그 구간의 시선·표정을 함께 확인. 점수가 아닌 관찰.
고도화 ④ RAG
포트폴리오 면접이 레포 내용을 실제로 반영하도록, 분석을 DB에 저장했다 꺼내 씀.
범위를 이렇게 좁힌 이유
졸업작품 시연에서 "확실히 동작하는" 것이 "많은데 어설픈" 것보다 낫다고 판단. 그래서 위 다섯 가지에 집중하고, 그 이상은 "남은 작업"으로 분리했습니다.

아키텍처 흐름 — 시스템은 어떻게 짜여 있나

화면(브라우저)에서 저장소(Supabase)까지, 요청이 어느 계층을 거치는지 정리했습니다. 핵심은 느슨하게 나뉜 4개 계층이며, 얼굴 영상은 브라우저를 벗어나지 않습니다.

① 브라우저
Next.js UI
화면 렌더 · 카메라/마이크 · 녹화 · 얼굴 분석. MediaPipe로 얼굴 랜드마크를 브라우저 안에서만 계산(서버로 영상·랜드마크 미전송), MediaRecorder로 마이크+면접관 음성을 믹싱해 녹화.
▲ HTTPS · WebSocket ▼
② BFF
Next.js API
인증 게이트 + 중계(프록시). 로그인 확인 후 FastAPI로 요청을 넘기고, 저장·조회 일부는 서비스 계정으로 DB에 직접 접근.
▲ HTTP · x-user-id ▼
③ AI 백엔드
FastAPI
실시간 음성 면접(WebSocket) · 리포트 생성 워커 · RAG 조회. 세션 상태를 DB에서 복원하고, 면접관 프롬프트를 구성해 Gemini Live와 연결.
▲ SQL · Storage ▼
④ 외부 서비스
Supabase — PostgreSQL(세션·녹화메타·시선·리포트) + Storage(영상 파일). Gemini Live — 실시간 음성 대화. Gemini — 리포트 텍스트·비언어 코칭 생성.
설계 의도
"화면은 Next.js가, 실시간 AI는 FastAPI가, 데이터는 Supabase가" — 각자 잘하는 일을 맡는 모듈러 구조. 영상 녹화·비언어 분석은 대부분 브라우저 계층에서 완결되고, 서버로는 관찰 수치만 올라갑니다.

구현 ① 영상 녹화 — 면접관 음성 포함

면접을 통째로 녹화하되, 본인 답변뿐 아니라 면접관(AI) 질문 음성까지 한 트랙에 담는 것이 핵심이었습니다. 리포트에서 질문·답변을 함께 들으며 되돌아볼 수 있어야 하기 때문입니다.

어떻게 만들었나

  • 녹화 — 브라우저 MediaRecorder로 카메라 영상을 녹화. 마이크와 면접관 재생 음성을 오디오 엔진에서 한 트랙으로 믹싱(크롬은 트랙이 여러 개면 첫 번째만 저장하므로 믹싱이 필수).
  • 저장 이중화 — 개발 환경은 public/local-recordings/ 폴더에, 배포 환경은 Supabase Storage에 서명 업로드. NODE_ENV로 자동 분기.
  • 재생 — 리포트에서 로컬은 정적 URL, 배포는 1시간 서명 URL로 불러와 재생(구간 점프 지원).

구현 ② 비언어 분석 & 질문별 리포트

면접이 끝나면 리포트에서 영상을 질문 단위로 되돌아보고, 그 구간의 비언어 행동(시선·표정)을 참고할 수 있습니다. 점수를 매기지 않고 "관찰된 행동"만 담백하게 보여주는 것이 기획 원칙입니다.

비언어 관찰
MediaPipe로 초당 5회 시선·표정을 관찰해 정면 응시%·미소%·고개 움직임(낮음/보통/높음)을 요약. 감정을 단정하지 않음.
질문별 하이라이트
타임라인 아래 Q1·Q2·Q3 칩을 펼치면 그 질문 구간만 재생하는 미니 플레이어가 열리고, 구간 끝에서 자동으로 멈춤.
구간 시선 요약
해당 구간의 정면 응시·미소 비율을 칩으로. 표본이 부족하면 표시하지 않고, 참고용임을 문구로 명시.
재생 오버레이
재생 중인 얼굴 위에 시선 점·상태 점을 얹어 어디를 보고 있었는지 직관적으로 표시. 끄고 켤 수 있음.

AI에게 무엇을 보내나

Gemini에는 영상을 보내지 않습니다. "정면 응시 80% · 미소 20% · 고개 움직임 보통" 같은 집계 숫자와 텍스트만 전달해, 감정을 단정하지 않는 행동 기반 코칭 문구를 생성합니다.

검증
시드 리포트에서 Q1~Q3 칩이 렌더되고, 펼치면 해당 구간(예: 0:12)으로 정확히 이동하며, 시선 오버레이와 구간 통계 칩(이탈 20%·미소 60%)이 함께 뜨는 것을 브라우저로 확인했습니다.

구현 ③ 포트폴리오 RAG-lite

"프롬프트에만 의존하지 말고, DB에서 꺼내 쓴다" — 포트폴리오 면접 고도화의 핵심입니다. 거창한 벡터 검색이 아니라, 레포 분석을 DB에 저장했다가 면접 시작 시 서버가 다시 꺼내(retrieve) 면접관에게 주입하는 가벼운 방식입니다.

단계동작
① 분석공개 깃 레포 URL → GitHub API로 README·파일트리 수집 → Gemini가 요약·아키텍처·인프라 가설·감지 토픽 추출
② 저장세션 생성 시 분석 스냅샷을 portfolio_sources 테이블에 저장 (기존엔 저장만 되고 아무도 안 읽던 "죽은 데이터")
③ 조회면접 시작 시 서버가 세션 종류를 보고 DB에서 스냅샷을 다시 읽어 면접 상태에 병합 (retrieve)
④ 주입구조화된 텍스트(레포/README/아키텍처/가설/토픽) + 60/10/30 평가 루브릭을 면접관 프롬프트에 주입
결정적 증명
웹소켓 초기화에 클라이언트 데이터를 일부러 빈 값으로 보냈는데도, 실제 레포 기반 포트폴리오 첫 질문이 정상 생성됐습니다 → 프롬프트가 아니라 DB 조회로 컨텍스트가 들어온다는 증거.
검증에서 잡은 함정
이 DB 조회를 실시간 음성 처리 도중 그대로 실행하면 서버가 잠깐 멈추는 문제가 있었습니다 → 조회를 워커 스레드로 분리해 다른 면접 세션에 영향이 없도록 고쳤습니다.

개발 중 해결한 문제 — 안정화

새 기능을 붙이는 과정에서 실제로 면접을 돌려보니 곳곳에서 조용히 실패하고 있었습니다. 발견한 문제를 근본 원인까지 추적해 고쳤습니다.

문제면접이 첫 질문에서 멈춤. 쿠키가 커지면(8KB↑) 웹소켓 첫 악수가 400으로 거부 + 최초 연결 실패 시 재시도 없음
해결핸드셰이크 헤더 한도 32KB로 상향 + 시작 전에도 자동 재연결 → 서버가 살아나면 자동으로 면접 시작(실측)
문제영상이 소리만 나오고 화면이 검음. 카메라 준비보다 녹화가 먼저 시작돼 오디오 전용으로 고정
해결카메라 스트림 도착을 기다렸다가 녹화 시작(실패 시 음성 폴백). 산출물 vp9 영상+opus, 프레임 밝기 정상 확인
문제면접이 자연스럽게 끝나면 영상이 사라짐. AI 종료 경로에서 업로드·저장을 건너뜀
해결자연 종료도 정식 종료 루틴을 타도록 배선 → 녹화·시선·리포트 요청 유실 방지
그 외
시선 분석 시간축 정렬 보정, 연결 끊김 중 녹화 영구 중단 방지, 배포 환경 전용 업로드 유실 버그 등 — 멀티에이전트 검증으로 확정한 결함까지 함께 수정했습니다(다음 장).

저장 용량 분석 — Supabase 무료플랜

영상은 용량이 크므로, 무료플랜으로 시연이 가능한지 실제 비트레이트로 계산했습니다. 결론부터: 시연에는 충분하며, 비트레이트를 낮춰 여유를 2배로 늘렸습니다.

전영상 1.5Mbps → 실측 ≈ 12.2 MB/분 → 7분 면접 ≈ 85MB
후영상 0.8Mbps로 하향(분석·재생 화질엔 영향 거의 없음) → ≈ 7 MB/분 → 7분 면접 ≈ 44MB
무료플랜 한도1회 소요수용량판정
Storage 1 GB7분 면접 ≈ 44 MB약 22회 저장시연 충분
Egress 5 GB / 월리포트 1회 시청 ≈ 44 MB약 116회 시청 / 월시연 충분
Database 500 MB세션당 시선 데이터 ≈ 25 KB수만 세션문제 없음
운영 시 참고
여러 명이 계속 테스트하면 Storage 1GB는 실면접 20여 회에서 참니다. 장기 운영 시 ① 오래된 녹화 자동 정리 ② Supabase Pro(Storage 100GB) 중 하나를 고려. 시연 단계에서는 현재 무료플랜으로 충분합니다.
